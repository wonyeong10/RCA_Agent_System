아이디어 3. Tool 중심 구조

- OpenRCA 최고 조합도 정답률 약 11% -> 병목은 "LLM이 거대 데이터를 직접 코드로 탐색하는 구조"
- 방향: 데이터 처리는 결정적 코드, LLM은 좁혀진 데이터로 판단만 (자유 코드·SQL 금지, 고정 시그니처 tool만)
- TAMO처럼 학습 모델을 tool로 쓰지 않음: 라벨 400건뿐이라 과적합·유출 위험, LLM 역할이 사라짐
- "모르면 다시 수집" 루프({status, missing} 구조화 출력)는 철회 -> finish tool 루프 (아이디어 4), 포기 성향 기각 (아이디어 5)
- 남은 검증 후보: 규칙만 vs 규칙+LLM vs 규칙+LLM+system card ("LLM이 왜 필요한가"에 답)
- LLM이 가치를 내야 할 지점: pod/service 영향 범위 판별, 비슷한 유형 구분(pod failure/kill, network delay/loss), 데이터 누락 케이스

아이디어 4. 전체 흐름 (2026-10-27 논의, 구현 기준으로 갱신)

- 전체 흐름
  input(uuid, 장애 구간) -> [reader] 시간대 변환·구간 자르기·정렬 -> [selector] 이상 패턴 선별 -> initial brief
  -> [Tool 모델] search 반복 -> finish -> [Answer 모델] json 답변 -> output.jsonl
- 전처리 필수: 16분 기준 log ~4만 줄, trace ~4만 span -> 원본 그대로 LLM 입력 불가
- 도메인 분리: reader = 원본 보존, selector = 정규화·quirk·선별 (아이디어 6, 7)
- initial 데이터 (확정): input 구간 고정, 코드가 고정 규칙으로 생성, 구간 안 모든 엔티티 대상
  - 이유: 첫 수집까지 모델이 정하면 첫 수집과 재검색이 섞이고, 사전지식 편향으로 node·TiKV 장애를 놓침
- Tool: search(sources, target, window) + finish. tool 3개는 같은 함수의 껍데기라 1개 + sources 리스트
  - window = {before_min, after_min} 0~60, 구간 확장 전용 tool 불필요. 그 외 tool 없음
- 루프 (확정)
  - 결정 호출과 답변 호출 분리: 결정 = tool_choice=required·reasoning 끔, 답변 = json_schema strict·reasoning medium·실패 시 1회 재시도
  - MAX_LOOPS 5 (근거와 무관하게 첫 호출 82%가 search라 상한 필수, tool 병렬 호출 가능), 소진 시 강제 답변
  - search는 병렬, finish와 섞이면 finish 우선. 형식 오류·중복 조회도 tool 결과로 돌려줌 (회차 소모)
  - search target 선택지 = 케이스별 entities(입력 ±60분): 구간 내만 주면 failure 장애의 원인이 빠지고, 시간대마다 활동 엔티티가 다름
  - 답변 선택지 = 전체 날짜 metric 행 주인 합집합 56개 (groundtruth 미사용)
  - 모델은 Pro 4 하나로 시작, Mini 4 분리는 ablation
- history: stateless라 매번 통째로 전달, append-only (프리픽스 캐시)
  - (2026-10-29 피드백) 누적 방식 검증 미완: 회차별 input 토큰 증가, 앞 회차 근거를 최종 판단에 쓰는지 -> 나쁘면 요약·잘라내기

아이디어 5. 답변 포기·근거 부족 신호 검증 (2026-10-28~30)

- 피드백: "모델이 답변을 포기하는 순간과 근거가 부족한 경우를 어떻게 알아내는가?"
- 문제: 시도율 41%는 closed-book 사실 질문 + 기권 옵션에서 측정 -> tool 선택 상황으로 옮겨온다는 근거 없음
- Upstage 예제 (solar_model_test/research-agent): "보류"는 프롬프트 규칙, 근거 부족 기준을 셀 수 있게 정의.
  채택 실행에서 라벨 0회·자가검증 거짓 -> 모델 자기 판정 신뢰 불가. 재검색도 404 재시도뿐
- 실험 v1 (2026-10-29, Experiments/abstain/output/2026-10-29_202346, 540 호출): "원인 근거가 빠진 것" 감지 못함 -> 포기 성향 활용 철회
  - L1·L2 조작이 비현실적이고 정답률은 느슨한 일치라 무효. 남는 관찰: 재검색은 "빠진 것"이 아니라 "보이는 것"을 따라감
- 실험 v2 (2026-10-30, Experiments/abstain/output/2026-10-30_133021, 840 호출, $3.17)
  - 근거 수준: L0 원인이 2개 이상 source에 보임 / L1a 원인 source 1개만 남김(인공) / N1 원래 1개 source / N0 어느 source에도 없음
  - 결과 (L0 / L1a / N1 / N0): A 포기율 8 / 4 / 11 / 16%, B 재검색률 81 / 80 / 67 / 86%, B target=정답 42 / 28 / 28 / 8% (무작위 ~11%)
  - 해석: 근거가 부족해도 답을 포기하지 않고(H1 기각), 재검색은 근거와 무관하게 습관적(H2 재검색 여부 기각), 재검색 대상은 보이는 근거를 따라감
  - 한계: 근거 수준 분류가 느슨한 일치 -> 엄격 재분류 시 L0 4~5건 -> 재설계 후 재실행 필요 (보류)
  - 설계 함의: 재검색 대상은 모델이 고름, 재검색 여부는 판정 수단이 없어 MAX_LOOPS로 막음, reasoning은 답변 호출에서만
- 코드 판정 규칙("원인 후보 이상 source < 2 -> 재검색") 보류: 정답 기준이면 유출, 모델 후보 기준이면 2개 이상 source 후보 27건 전부 오답
- 구현 중 발견: json_schema strict에서 긴 문자열 뒤 공백 반복 -> 다음 키 누락 -> reason을 마지막 필드로 (파일럿 2/9 -> 1%)

아이디어 6. reader 설계 (2026-10-28)

- 핵심 원칙 (연구실 보고 기준)
  1) 원본을 최대한 훼손하지 않고 원시 작업만. 도메인·외부 지식을 넣지 않음
  2) 모델의 유동적인 재검색 지시(구간·entity·source)를 정확히 읽어옴
  3) 모델 지시 오류는 전처리가 아니라 Loop에서 미리 검사 -> 전처리 독립성
- 역할: 원본 보존 + 시간대 변환 + 구간 자르기 + 정렬만. 정규화·quirk는 selector로 (정규화하면 selector가 쓸 정보가 사라짐)
- target 확장 없음: 모든 target이 "행 주인 == name"인 자기 데이터만
  - 경과: service가 이름 패턴으로 pod를 끌어오게 했다가 되돌림 (<service>-N 규칙도 외부 지식, node->pod를 안 따라가는 것과 일관성 깨짐)
  - node 유지: node 장애 82/400건, node 지표는 node target으로만 나옴
  - 관계 지식(pod 목록, service<->pod, pod->node)은 system card 3층으로. replica·node 비교는 모델이 병렬 호출
- 선택지 목록: 장애 구간이 아니라 넓은 구간에서 추출 (pod failure면 구간 안에서 pod가 사라짐), tool enum + 코드 검증
- coverage 삭제: 엔티티 단위로 제대로 하려면 구현이 끝없고 source 단위로는 의미가 약함 -> 빈 결과 해석은 프롬프트 규칙 ("행 0 = 정상 근거 아님")
- 엔티티 종류별로 source가 없다고 미리 판단하지 않음 (외부 지식이라 제거), 대가는 빈 결과 읽기 ~1-2s
- TiDB 계층 metric instance는 엔티티 이름이 아님 -> target은 컴포넌트 단위, groundtruth tidb-tikv-0 표기는 채점·출력 단계 매핑
- Agent Loop 입력 검사 (reader 앞단, loop.py validate에 반영 완료)
  - 시간대 없는 ISO를 reader가 KST로 해석해 9시간 어긋난 구간을 오류 없이 반환 -> 모델은 시각을 쓰지 않고 window만, 시각은 코드가 계산
  - 비문자열·비dict target의 TypeError·AttributeError -> 스키마·타입 검증 후 넘김
- 검증 (Tests/Preprocessor/reader/test_reader.py, 독립 oracle과 행 단위 대조): PASS 95 / FAIL 0 / INFO 4 (INFO = Loop로 넘긴 입력 검사)
  - 400건 전수: 예외 0, 건당 평균 2.4s·최대 7.6s, 행 0 케이스 log 21 / trace 40 (data/CLAUDE.md와 일치)

- 순서 결정: 가설 실험의 brief가 실제와 형식·노이즈가 같아야 결론이 유효 -> selector 먼저 구현
