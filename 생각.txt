아이디어 3. Tool 중심 구조 + "모르면 다시 수집" 루프

- OpenRCA 최고 조합도 정답률 약 11% -> 병목은 추론보다 "LLM이 거대 데이터를 직접 코드로 탐색하는 구조"
- 방향: 데이터 처리는 결정적 코드, LLM은 좁혀진 후보 중 판단만 (자유 코드 생성 금지, 고정 시그니처 tool만)
- TAMO처럼 학습 모델을 tool로 쓰진 않음: 라벨 400건뿐이라 과적합·유출 위험, LLM 역할이 사라짐
  -> tool은 통계·규칙 기반 (baseline 대비 z-score, 에러율 급증, trace 간선별 지연 변화)
- 역할 분담
  1) 전처리(코드): 시간 변환·필터, 소스별 커버리지
  2) 이상 탐지(코드): 엔티티(pod/service/node/TiDB)별 metric·log·trace 이상 점수 -> 후보 상위 N + 근거 표
  3) 전파 보정(코드 + system card): 토폴로지로 상위=증상, 하위=원인 점수 조정
  4) 판단(LLM): 후보 표 + system card로 위치·유형 결정, 필요 시 get_entity_metrics / get_edge_traces / get_pod_logs 호출
  5) 출력(코드): fault_type 18종·instance 형식 검증, reason에 kpi_key 지표명 포함
- "모르면 다시 수집" 루프 (Solar의 답변 포기 성향 활용)
  - LLM 출력을 구조화: {status: answer|insufficient, candidates, missing:[{entity, source, window}]}
  - insufficient -> 코드가 missing대로 추가 수집 (후보 세부 지표 -> 토폴로지 이웃 -> 시간 구간 확장 -> 다른 소스)
  - N회차(예: 3)엔 insufficient 금지, 최선의 답 강제 (채점은 모든 케이스에 답 필요, "모름"=0점)
  - 코드 기반 점검 병행: 1·2등 점수 차 크면 바로 답, 차이 작은데 확신하면 한 번 더 수집
  - 커버리지를 모델에 알려 없는 데이터(trace 없음 40건, log 없음 21건) 요청 방지
    -> (2026-10-28 변경) reader coverage 삭제, 빈 결과 해석은 프롬프트 규칙으로. 아이디어 6 참고
  - 주의: AA-Omniscience는 사실 지식 시험 -> "근거 충분성 판단"으로 이어지는지는 직접 측정해야 함
  - 과도한 포기(시도율 41%)로 루프·지연 늘 위험 -> 회차 상한 필수
- 검증 실험
  - 규칙만 vs 규칙+LLM vs 규칙+LLM+system card ("LLM이 왜 필요한가"에 답)
  - 강제 답변 vs 포기 신호 루프: 정확도·평균 회차·응답 시간
  - 포기 신호 신뢰도: "충분" 판단 시 실제 정답률, "부족" 후 추가 수집으로 정답률이 오르는지
  - LLM이 가치를 내야 할 지점: pod/service 영향 범위 판별, 비슷한 유형 구분(pod failure/kill, network delay/loss), 데이터 누락 케이스, reason 작성

아이디어 4. 전체 흐름 정리 (2026-10-27 논의)

- 전체 흐름
  input(uuid, 장애 구간) -> [reader] 시간대 변환·필터·정렬·정규화 -> [selector] baseline 대비 이상 탐지로 필요한 데이터만 선별
  -> initial brief + system card -> [결정 LLM] tool 선택 반복 -> finish -> [답변 LLM] json 답변 -> 출력 검증 -> output.jsonl

- 전처리 필수: 장애 구간만 잘라도 원본이 너무 큼 (16분 기준 log ~4만 줄, trace ~4만 span) -> 원본 그대로 LLM 입력 불가

- 도메인 분리 (확정)
  1) reader: 시간대 변환(파일명 CST / 내부 UTC), 시각 필터, 정렬, 컬럼 정규화(ts, service, pod, node), 데이터 quirk 흡수
  2) selector: 정렬된 데이터에서 이상 탐지 기반으로 필요한 데이터만 선별
  -> 데이터 quirk는 reader 밖으로 새지 않게
  -> (2026-10-28 변경) reader는 원본 보존 + 시간대 변환·정렬만, 정규화·quirk는 selector. 아이디어 6 참고

- 데이터 표현: OpsAgent(텍스트로 통일) vs TAMO(시계열 + 딥러닝 학습)
  - 양자택일 아님: 계산용 표현(정렬·비교)과 LLM 입력 표현은 다른 층. Solar 입력은 어차피 텍스트
  - 방향: 시계열로 정렬(TAMO식, 딥러닝 대신 통계 z-score) -> 이상 부분만 텍스트로(OpsAgent식)
  - 시계열 층을 두는 이유
    - source 간 시각·엔티티 맞추기를 LLM에 맡기지 않음 (LLM은 긴 텍스트 속 숫자·시각 대조에 약함)
    - onset(누가 먼저 튀었나) 계산 -> 원인/증상 구분 단서
    - LLM 없이 recall@K(후보에 정답 포함 비율)로 전처리 품질 검증 가능
  - log·trace는 분 단위 count로만 줄이면 의미 손실 (로그 내용, 호출 트리, 1초짜리 장애) -> 집계는 선별용, 근거는 원본에서
    - log: 숫자·ID 마스킹으로 템플릿화 후 집계, 구간에 새로 등장한 템플릿이 핵심 신호
    - trace: 호출 트리 복원 후 self_time(자기 duration - 자식 duration) -> 지연이 실제로 생긴 위치 특정
    - onset은 집계 단위가 아니라 원본 첫 이상 이벤트 시각
    - 원래 텍스트인 정보(템플릿 문장, 에러 메시지, trace status.message)는 원문 유지
  - 실험: source별 텍스트 요약만(OpsAgent식) vs 시계열 정렬 -> 텍스트, 같은 LLM·케이스로 정확도·토큰 비교

- initial 데이터 (확정)
  - input 장애 구간 [start, end]로 고정, 코드가 고정 규칙으로 생성
    (첫 수집 범위까지 모델이 정하면 "첫 수집"과 "재검색"이 섞여 tool 설계가 애매해짐)
  - 구간 안 모든 pod·service·node·TiDB 계층 포함
    (모델은 장애 위치를 모름. 처음부터 모델이 고르게 하면 사전지식 편향으로 node·TiKV 장애를 놓침)
  - 압축: (엔티티, signal)당 1행 - baseline, 구간 평균·최대, z, onset. 이상 행만 상세, 나머지는 엔티티별 "정상 n개" 한 줄
  - 엔티티 종류별 따로 Top-K (frontend 등 시끄러운 상위 서비스가 node·TiKV 후보를 가리지 않게)
  - baseline 값을 열로 함께 넣음 (없으면 값이 이상한지 판단 불가). 코드 규칙이지 모델 판단 아님
  - 원인 시점이 구간 밖일 수 있음 -> onset이 구간 경계에 붙으면 "구간 앞 원인 가능" 표시, 확장은 tool로
  - 현재 데이터셋은 input 시각 = groundtruth 시각 -> dev 날짜에서 실제 onset이 start에서 얼마나 벗어나는지 먼저 확인

- system card 활용
  - 아이디어 1의 3층 + 추가 2개: signal 카탈로그(사용 가능한 kpi_key 목록), 케이스별 데이터 커버리지
    -> (2026-10-28 변경) 케이스별 커버리지 대신 일반 규칙("행 0 = 정상 근거 아님") + observability. 아이디어 6 참고
  - initial 단계가 아니라 tool 단계에서 "어느 엔티티를 더 볼지" 고르는 근거

- Tool 설계
  - get_metrics / get_traces / get_logs / finish
  - 모델이 엔티티와 window 지정. window = {before_min, after_min} (input 구간 기준 앞뒤 확장, 0/0 = 원 구간) -> 구간 확장 전용 tool 불필요
  - get_metrics: service 지정 시 소속 pod 나란히, node 지정 시 올라간 pod 포함 (pod vs service 범위 판단)
  -> (2026-10-28 변경) tool 1개 + sources 리스트, node는 자신만. 아이디어 6 참고
  - 반환은 baseline 대비 요약, raw 덤프 금지
  - 그 외 tool 추가 안 함 (이웃 조회=system card, 커버리지=initial, replica 비교=get_metrics). 자유 코드/SQL 실행 배제

- 루프 (확정, 아이디어 3의 {status, missing} 구조화 출력 대신 finish tool 방식)
  - 결정 호출과 답변 호출 분리
    - 결정: tool_choice=required, reasoning 끔 -> 검색 tool 또는 finish
    - finish -> 답변 호출 1회: json_schema strict (fault_type enum 18종, instance 형식), reasoning 켬
  - 포기 신호 = finish 대신 검색 tool 호출 -> finish까지 회차 수로 측정
  - MAX_LOOPS 소진 시 결정 호출 건너뛰고 바로 답변 호출 (강제 답변)
  - tool arguments가 깨진 JSON -> 검증 후 오류를 tool 결과로 돌려줌 (회차 소모)
  - 모델은 하나(Pro 4)로 시작, Mini 4 분리는 ablation

  - 이미 읽은 결과 재투입: 대화 history 자체 (Responses API stateless라 매번 통째로 전달) -> 별도 캐시 불필요
  - 중복 읽기 방지: 케이스별 메모리 dict (tool, entity, window) -> 겹치는 구간이면 새 구간만 읽음
  - ContextVar: 케이스를 스레드로 병렬 실행할 때만 필요 (copy_context 필수). 순차 실행이면 dict로 충분
  - (2026-10-29 피드백) history 누적 방식 검증 필요 -> Loop 설계 시 테스트

    -> L0 정확도 자체가 낮음 -> 포기 신호와 별개로 판단 단계(system card, 프롬프트) 보강 필요
  - 비용·시간 (호출당): A $0.005·평균 37.6s·최대 189s (reasoning 3.3k 토큰), B $0.0009·1.2s
  - 구현 중 발견
    - json_schema strict에서 긴 문자열(reason) 뒤 공백 무한 반복 -> 다음 키 누락 (파일럿 2/9) -> reason을 마지막 필드로 옮겨 1%(3/270)로 감소, Loop엔 재시도 1회 필요
    - instance에 설명문 섞임 -> "이름 하나만" 프롬프트 규칙
  - 한계: 첫 결정만 (재검색 후 회복 미측정), system card 없음, 30건 × 3회
- 실험 v2 (2026-10-30, Experiments/abstain/output/2026-10-30_133021, 840 호출, $3.17, 67.6분, 오류 4)
  - v1 L1·L2 교체 이유: 원인을 3 source 전부에서 지우거나 이상 줄 전부 삭제는 현실에 거의 없는 조건
  - 근거 수준 ("보인다" = 정답 엔티티가 주인인 줄)
    - L0: 원인이 2개 이상 source에서 보임 (원본) / L1a: 같은 케이스에서 원인 source 1개만 남김 (인공)
    - N1: 원래 1개 source에서만 보임 (자연) / N0: 어느 source에도 안 보임, 10분 초과 (자연)
    - Nshort(10분 이하) 제외: 근거 수준이 섞이고, "판정 불가"가 떠도 window 확장이 늘지 않음 (51%)
  - 결과 (L0 / L1a / N1 / N0)
    - A 포기율: 8% / 4% / 11% / 16%
    - B 재검색률: 81% / 80% / 67% / 86%
    - B target=정답 (엄격): 42% / 28% / 28% / 8% (무작위 기준선 ~11%)
  - 해석: 근거가 부족해도 답을 포기하지 않고(H1 기각), 재검색은 근거와 무관하게 습관적(H2 재검색 여부 기각).
    다만 재검색 대상은 보이는 근거를 따라감 (무작위보다 높음)
  - 엄격 재채점 (참고): A instance 정답 L0 63% -> 14%
  - 한계: 근거 수준 분류가 느슨한 일치 -> 엄격 재분류 시 L0 4~5건 -> 실험 재설계 후 재실행 필요 (보류)
  - 설계 함의: 재검색 대상은 모델이 고름, 재검색 여부는 판정 수단이 없어 MAX_LOOPS로 막음, reasoning은 답변 호출에서만, 재시도 1회

아이디어 6. reader 설계 (2026-10-28 논의, 아이디어 4의 reader·tool 항목 갱신)

- 핵심 원칙 (연구실 보고 기준)
  1) 원본을 최대한 훼손하지 않고 원시 작업만. 도메인·외부 지식을 넣지 않음
     -> 시스템 구조·도메인 지식이 바뀌어도 reader는 안 고침, selector는 원본이 살아 있어야 제대로 고름
  2) 모델의 유동적인 재검색 지시(구간·entity·source)를 정확히 읽어옴 (단방향 1회 실행이 아니라 Tool 루프)
  3) 모델 지시 오류는 전처리가 아니라 Loop에서 미리 검사 -> 전처리 독립성
- 내부 처리 순서: 파일 선택(UTC 구간 -> CST 파일명·날짜 폴더, metric은 target type·name으로 파일) -> 시각 필터(읽을 때 pyarrow filters)
  -> target 행 필터(infra_pod·infra_node처럼 여러 엔티티가 섞인 파일만, log·trace는 행 주인) -> ts 정렬·날짜별 file_key 이어 붙임

- 역할 변경: reader = 원본 보존 + 시간대 변환 + 구간 자르기 + 정렬만. 정규화·quirk 처리는 selector로
  - 이유: 내부 정보가 살아 있어야 selector가 고름. 정규화하면서 버리는 정보(trace logs, tags 대부분, 노드 IP 등)가 생김
  - 추가 열은 ts(UTC) 하나, 빼는 열은 kpi_name 하나. 'null' 문자열·대소문자·operationName 등 원본 그대로
  - 출력: {log: DF, trace: DF, metric: {file_key: DF}} (요청 source만). metric은 파일마다 스키마가 달라 파일 1개 = DF 1개
  - source 개수와 무관하게 같은 모양, 합치지 않음, 호출자는 항상 selector로 넘김
- 인터페이스: read(sources, target, start_time, end_time)
  - sources 복수: tool 1개 + sources 리스트 (tool 3개는 같은 함수의 껍데기일 뿐)
    - 비용은 LLM 호출 수 기준 -> source별로 구간이 다르면 같은 tool을 인자만 바꿔 병렬 호출 (per-source window 인자 불필요)
  - target: None(initial) | {type: pod|service|node|tidb|tikv|pd, name}
    - node 유지: node 장애 82/400건은 정답이 node명(service 빈 값), node 지표는 node target으로만 나옴
    - type은 metric 폴더 분기에만 씀 (모델이 kpi까지 고르진 않음, metric 하루 ~2MB라 전부 읽고 selector가 추림)
  - 확장 기준 (2026-10-28 최종): 확장 없음, 모든 target이 "행 주인 == name"인 자기 데이터만
    - 경과: pod를 빼고 service가 이름 패턴(^{name}-\d+$)으로 하위 pod를 끌어오게 했다가 되돌림
      -> <service>-N 명명 규칙도 k8s 배포 방식에서 온 외부 지식, node->pod 배치를 안 따라가는 것과 일관성 깨짐
      -> service 자신의 log·trace 행은 원래 없음 (log·trace 주인은 항상 pod)
    - pod: apm pod 파일 + infra_pod 행 + log·trace 행 / service: apm service 집계 파일만 / node: infra_node 행만 / tidb·tikv·pd: 각 파일
    - replica 비교·node vs pod 비교는 모델이 pod target을 병렬 호출해서 (LLM 호출 1회 유지)
    - 관계 지식(pod 목록, service↔pod, pod->node)은 전부 system card 3층(selector가 initial에서 생성) -> ablation 가능
    - 호출자 client span은 안 넣음 (frontend -> adservice span은 frontend 데이터)
    - 관찰: infra_pod에만 있고 log·trace가 없는 pod 존재 (06-06 00시: checkoutservice-0/1, recommendationservice-1/2) -> 활동 replica ≠ metric상 pod 목록, selector 참고
  - 선택지 목록: target은 케이스별 데이터에서 추출, 장애 구간이 아니라 baseline 포함 넓은 구간에서 (pod failure면 구간 안에서 pod가 사라짐)
    tool 스키마 enum(케이스별 동적) + 코드 검증
- 시각 필터: 양끝 포함 [start, end], 초 정밀도
  - log @timestamp: 경계를 "...SS.000Z"/"...SS.999Z"로 맞춰 문자열 비교 (그대로 쓰면 "...02.045Z" < "...02Z" 참 -> 경계 행 누락)
  - trace startTime(μs) span 시작 기준 / metric time 분 내림 (안 하면 1초 장애는 metric 0행)
  - 실측: 모든 파일 row group 1개 -> pushdown 프루닝 없음. trace 1시간 필터 읽기 0.25s, log 0.03s -> 캐시 불필요
- target 행 필터: 모든 source에 같은 규칙 (행 주인 = log k8_pod, trace pod 태그, apm 파일명, infra pod/kubernetes_node가 target 이름과 같으면 남김)
  - 특정 엔티티 종류에 source가 없다고 미리 판단하지 않음 (2026-10-28, 처음엔 node·TiDB의 log·trace를 not_applicable로 막았으나 외부 지식이라 제거)
  - 대가: service·node·TiDB target에 log·trace 요청 시 파일 읽고 빈 결과 (~1-2s)
- coverage (2026-10-28 삭제) -> "없음"의 해석은 LLM 프롬프트의 도메인 지식으로
  - 경과: no_file / gap / no_target_rows / ok 상태를 reader가 판정했으나
    initial(target=None)에선 source 전체 수집 중단만 잡고(no_target_rows 불가), metric은 109파일 합산이라 거의 항상 ok
    -> 엔티티 단위로 제대로 하려면 구현이 끝없음, source 단위로는 의미가 약함
  - 지금: reader는 데이터만 반환. 빈 DataFrame = 그 구간·target에 행 없음 (파일 없음·구간 공백·엔티티 없음 구분 안 함, 모델엔 셋 다 "근거로 못 씀")
    - 분 단위 공백은 selector가 분 집계할 때 빈 분으로 드러남. 엔티티별 존재 여부(pod별·file_key별 분 수, baseline 대비 사라짐)도 selector가 데이터에서 계산
  - system card에 넣을 규칙 (날짜별 누락표 같은 데이터셋 사례 목록은 안 넣음)
    - "source 행 0 = 수집 안 됨 또는 해당 엔티티 데이터 없음. 정상의 근거로 쓰지 말 것"
    - observability: ad·currency·payment·redis-cart는 trace 없음, node·TiDB 계층은 log·trace 없음, productcatalog 로그 거의 없음
- 배치표(pod 목록·pod->node): reader가 아니라 selector가 initial에서 생성 (원본에서 쌍을 뽑는 건 요약 작업)
- selector 참고용 사전 지식 (18일 스키마 전수 + 날짜별 trace 샘플, 2026-10-28)
  - 스키마 18일 동일. trace 태그 체계 서비스별 1종, 날짜 무관
  - trace: pod/node 키 name/node_name (cart·redis는 podName/nodeName), recommendation·email kind 대문자,
    callee rpc.service (python CLIENT는 없음 -> operationName 파싱, redis는 net.peer.name),
    status status.code (cart는 grpc.status_code, redis 없음), cart operationName "POST " 접두, references 0개 또는 CHILD_OF 1개
  - metric: 빈 값 = 문자열 'null', apm *_ratio int64/double 혼재,
    kpi_key 충돌(cpu_usage·memory_usage는 tidb/tikv/pd, qps·server_is_up은 tidb/tikv) -> (object_type, kpi_key)로 구분
    TiDB 계층 instance는 엔티티 이름 아님 (tidb 행에 tikv 포트, tikv 행에 node-exporter IP, pd 대부분 'null')
    -> target은 컴포넌트 단위, groundtruth tidb-tikv-0 형식 매핑은 출력 단계
    파일 접두(infra_tidb_/infra_tikv_/infra_pd_) ↔ object_type 1:1
    infra_pod에 example-ant-10-<숫자>-N pod (namespace hipstershop, 정체 미상)
- metric dtype 승격 (selector 참고): 일 파일마다 그날 값이 전부 정수면 int64, 아니면 double로 저장됨
  -> 18일 중 날짜별 타입이 다른 (파일, 열) 58개 (apm *_error_ratio 55, node_sockstat_TCP_inuse, tidb duration_avg·failed_query_ops)
  -> 단위 차이 아님 (ratio는 둘 다 퍼센트, int 날은 대부분 전부 0)
  -> reader가 CST 자정 넘는 구간에서 같은 file_key를 이어 붙이면 열 전체 float64로 승격. 값 손실 없음, dtype만 바뀜
  -> groundtruth 구간엔 없음, window 확장·전날 baseline에서 발생 가능. selector는 날짜 간 비교 시 어차피 float로 통일

아이디어 7. selector 설계 (2026-10-29 논의·구현, OpsAgent 전처리 그대로)

- 순서 결정: 피드백 "Solar가 근거 부족 시 정말 답변을 포기하는지 먼저 검증해야 재검색 Tool 설계가 뒷받침된다"
  - 실험안: 근거가 부족한 케이스를 만들어 답변 생성 트랙(보류하는가) / Tool 선택 트랙(재검색 tool을 부르는가) 행동 관찰 (아이디어 5 실험안과 같음)
  - reader 출력으로 따로 만든 brief는 실제와 형식·노이즈가 달라 결론이 약함 -> selector 먼저, 그 출력으로 실험
  - selector는 루프 앞단이라 가설 결과와 무관 (결과에 따라 바뀌는 건 루프 종료·재수집 규칙뿐) -> 선구현해도 버릴 위험 없음
- 원칙: OpsAgent(참고논문/OpsAgent.pdf 3.2 Training-free Data Processor)를 그대로 따르고 3가지만 반영
  1) 데이터셋 차이 2) 조회 구간이 바뀌는 Loop 3) target이 한정될 수 있음
- OpsAgent 원문 요약
  - metric: 3-sigma -> CNN 모양 분류(앞 20 / 뒤 10 포인트) -> <instance, metric, 모양: 시각, kσ> 정렬 -> Top-5 instance, Top-5 metric
